DartHub

A connected darts platform that brings physical or simulated boards, live scoring and multi-venue tournaments into one system.

Java 25MQTTSpark JavaSQLiteJWT RS256JUnit 5
Source repository ↗ No live demo published

Problem & user context

Players and venue operators need a shared view of games that span physical boards, simulated sensors and central services. The system must deliver timely scores without making the scoring experience depend on a perfectly stable connection.

Users

Players need reliable score updates; venue staff need to organize matches and tournaments; the edge display needs to keep up with throws.

Goal

Separate the physical-device boundary from tournament and venue management, while keeping scoring behavior consistent across edge and server components.

Architecture & data flow

The documented implementation contains ten modules, including six REST microservices with separate SQLite databases, a Spark Java API gateway, an edge component and a sensor simulator. HTTP handles service APIs; MQTT carries device events and commands.

Constraints & trade-offs

Offline resilience

A temporary disconnect should not silently discard a throw. The edge buffers throws locally and reconciles them on reconnect, so the interface can continue to score while connectivity is restored.

Consistent scoring

The scoring Strategy is shared between server and edge. This avoids maintaining separate scoring rules in two execution locations.

Service boundaries

Separate REST services and SQLite stores isolate domain responsibilities, at the cost of more modules and communication paths to test and operate.

Access control

The Spark Java gateway provides HTTPS and verifies RS256 JWTs before forwarding protected requests.

Results & lessons

10documented modules in the system
6REST microservices with separate SQLite stores
0*lost or duplicated buffered throws after reconnect, per project documentation

*This is a documented reliability behavior, not a published production benchmark. No live-user, latency or throughput measurements are currently published.

The key lesson was to make the edge-to-service boundary explicit: device events need buffering and reconciliation, while scoring logic should stay shared. JUnit 5 tests cover the Java components.
